### M2.2 关键决策与挡路的坑

1. **移除 `icon` / `cover` 不能写成 `upsert(id, { icon: undefined })`——sel §7 那一行今天不成立。** 证据链：`NodeService.upsert` 先 `const merged = { ...oldNode, ...updates }`（`packages/services/src/graph/node.service.ts:50`）再 `mutate({ id, updates: merged })`（`:58`、`:76`）；服务端 `updateSchema` 是 `z.object`（`backend/adapter-front/src/trpc/router/node.ts:259-273`），M1 之后会含 `icon`/`cover`；而 `updateNode` 的判断是**值判定**（`if (cmd.isPinned !== undefined)`，`backend/application/src/commands/node/node-command.service.ts:290-292`）→ `undefined` 一律表示「本次不动」。客户端又用 superjson（`packages/api-client/src/trpc/client.ts:41`、`backend/adapter-front/src/trpc/server.ts:69`），`undefined` 会被原样保留而不是当缺键丢掉，所以服务端**确实**收到这个 `undefined` 然后什么都不做。→ 清空需要一个非 `undefined` 的哨兵（`null`，或一个显式的 `removeIcon` 布尔），**由 M1 在 command 层定死**；本章的 `onRemove` 按 M1 落地的那一个写。这是本章唯一的跨章阻塞点，也是 G2 第 7 条的实测点。
2. **sel §11-2 的抓包判据要改写。** 线上发的是**整份合并后的节点**（`node.service.ts:50` + `:58`），不是 `{ icon }`，所以「`updates` 里只有 `icon`」永远看不到。正确判据：`updates.icon` 有新值，且 `updates.content`（以及 PB 的 `nodes.content` 列）与操作前**逐字段一致**。G2 第 2/8 条按这个写。
3. **两张图标表必须一起改。** `preview-header.tsx:18-29` 的 `nodeTypeIcons` 与 `node-preview-cover.tsx:32-43` 的 `NODE_TYPE_ICONS` 是同一份东西；W1-C 里只改一处就会出现「本地表又长回来」。整合后两处都 import `node-media/node-type-icons.ts`。
4. **`NodePreviewCover` 必须继续是叶子。** 它的自我约束写在 `node-preview-cover.tsx:13`（no store, no `PreviewHeader`），所以 `resolveNode` 只能是**可选 prop**、由宿主注入（sel §6.2）。R1 的 `NodePreviewBody` 不渲染 `NodePreviewCover`，因此 M2 **不需要**动 `packages/graph`（那是 M8 的面）。
5. **`{kind:"node"}` 的环保护 = 深度上限 1，而卡片侧不接第二层。** sel §8 明写不改 `dataview/src/shared/{card-cover,card-ops}`，于是 `card-cover.tsx:142-144` 那条分支不会把 `resolveNode` 往下传：「节点自身的封面又是 `{kind:"node"}`」在卡片上最多解析一层，第二层回落类型图标。**这是有意接受的限制**，登记进文末待验证；`NodePreviewCover` 内部仍必须防自引用（`A.cover = {kind:"node", nodeId: A}` 不能递归）。
6. **R4 的 content 半边只能由组件写，不能由模块级 helper 写。** `applyPdfAnalysis`（`file-drop-zone.tsx:197-220`，含 `:215` 的 `upsert`）与 `applyVideoTranscode`（`:234-264`）今天是模块函数；`useNodeContentWriter` 是 hook，只能在 `UploadDropZone`（`:270` 起）里调。做法：三个 helper 退化为**只产出本半边**（`contentHalf` + `meta`），由 `UploadDropZone` 做「读活 content → `{...live, ...half}` → 串行写」。**合并的对象必须是客户端的 `content` 对象（DTO 形状），不是 `nodes.content` 列的形状**——同一列在不同类型下存的东西不同：text 存 `docs` 对象（`node.mapper.ts:474-479`），image / pdf / video / audio 存的是 url **字符串**（`:481-491`、`:493-499`、`:501-516`）。照列形状拼会把 `{url}` 塞进一个字符串列。
7. **新 variant 不能复用 `image` 分支。** image 分支写 `content: { url }` + `width/height`（`:171-178`），拿它当封面等于把节点内容换成封面图（数据损坏）。`icon` / `cover` 两个分支只写**顶层**字段（`{ cover: { kind:"image", url } }` / `{ icon: { kind:"image", value: url } }`）。

17. **只读孪生要显式区分「可编辑的 `latexInline`」与「静态烘好的公式」。** `generateHTML` 不跑 node view，而可编辑的 `latexInline.renderHTML` 只吐一个空的 `span[data-type=latexInline]`（内容由 node view 填）⇒ 静态渲染会得到**看不见的公式**。所以 `createSingleBlockExtensions({ static: true })` 换成 `LatexInline.extend({ renderHTML })`：KaTeX 直接烘进 HTML（`document` 不是新增依赖面 —— `generateHTML` 本身就是 DOM-bound 的）。`SingleBlockRenderer` 今天仍无消费方（遗留 1），但公式进了文档形状，只读路径就不能再默认"文本而已"。
18. **参考图给的是一条位置关系，不是一个尺寸表（第 12 行）。** 量图（`/tmp/measure`，3061×1028 的截图，按内容列 708px + 3rem 反推 DPR≈2.4）得到的 CSS 值：封面 `1244×287`、圆角 10px、距 pane 边缘 8px；图标板 `91×91`、**左边缘与文字列左边缘对齐**；板底在封面下沿**以下 24px**（板顶则在上方 67px，即封面下方约 25% 处）；标题的墨迹顶在封面下沿以下 43px；摘要与 meta 依次差 ~15px；meta 是灰色（`rgb(130,130,130)`）而摘要是正文色（`rgb(37,37,37)`）。**落到本仓**（Dialog 1200×80vh ⇒ pane 1008、内容列 708）：封面 `h-60`=240、`rounded-lg`=10px、板 `size-20`=80 / 露出 16px、标题从 `text-3xl` 提到 `text-4xl`。两条**关系**比数字重要：① 封面比文字列宽（`cover.width == pane.clientWidth`，实测 1008 vs 708+2×48）；② `plate.top < cover.bottom < plate.bottom`。
19. **「封面出列」是宿主改动的全部内容，也是它唯一能出列的办法（第 12 行）。** 旧形态是宿主的 `<div className="mx-auto w-full max-w-[708px] px-12 pt-6">` 把整个头部（含封面）关进文字列，所以封面最多只能和正文同宽。现在**列由头部自己画**：根节点是满宽的 `flex flex-col`，封面是根的第一个孩子（`w-full`），文字列是第二个孩子。宿主因此**不再包那一层**；任何把 `NodeContentHeader` 包进窄容器的宿主都会把封面重新关回去。
20. **骑边用「行只定位自己的底」，不定位板（第 12 行）。** 图标行是 `h-10 items-end` 的定高盒 + `-mt-6`：负边距挪的是**行**（行底 = 封面下沿 + 16px），板在行内底对齐 ⇒ **板高多少都不影响这条关系**（当时的反例是 80px 的 emoji 大板与 44px 的 Lucide 小板露出量完全相同，探针 ⑳㉙㉚ 各测一次；r1 之后三种图标都统一成 80px 板，这条关系仍然由定高盒保证）。第一版按"板要往上挪 56"写成 `-mt-14`，实测板底落在封面下沿**以上** 16px（探针当场报 `露出=-16`）—— 定高盒 + `items-end` 就是为了让这类算术只出现一次。
21. **plate 一律 80px，字形按盒子比例给（第 14 行，用户追加要求「图标大小应该和 emoji 一样大」）。** emoji 是文字（plate 的 `text-5xl` = 48px），image 撑满盒子，两者天然跟着盒子走；`kind:"icon"` 的 Lucide 字形原先写死 `size-4`（sel §5），在 80px 板里只有 16px ⇒ 一开始我按「字形不会长大」给这种图标配了 44px 小板，用户实测后直接否掉：**参考图里图标只有一种大小，页头不该按图标种类分档**。修法是给 `NodeIconView` 加**可选** `glyphClassName`（默认不变 ⇒ 既有消费方源码与观感零变化），页头传 `size-3/5`；`NodeIconViewProps` 是 W1-A 的冻结形状，加**可选**字段是纯增量，但文件本身超出本章白名单，所以在 §M3.1 第 14 行与 [gates.md](./gates.md) 里显式登记。三处（注入的触发按钮、头部的 `fallback` 板、字形）共用 `NODE_ICON_PLATE` / `NODE_ICON_GLYPH` / `NODE_ICON_FALLBACK` 三个导出常量，各写一份类名必然漂移（探针 ㉒ 断言触发按钮与 `NodeIconView` 的盒子同尺寸）。
22. **第 5 段从「语义 pill」变成「类型 • 语义」（第 13 行）。** 参考图的 meta 行是两个 token（`Page • Tag`）：前者是节点类型、后者是语义。做法是 `NODE_TYPE_LABELS[node.nodeType]` + `•` + 原来的彩色 pill —— **表从 `menu/node/data-type-list.tsx` 复用**（复制第二份必然漂移，§M2.2-3 的图标表就是先例），**pill 的底色/文字色保留**（`semantic.color` 是分类自己的颜色，sel §4，不是这行可以丢掉的装饰）。副作用：没有语义的节点也有一行 meta（只有类型标签），头部元素个数不再随语义有无而变。
23. **参考图的摘要是正文色，本章没跟（第 21 条专判）。** 量图结果：摘要是 `rgb(37,37,37)`（正文色），只有 meta 是灰的。本章保留 `text-sm text-muted-foreground`：摘要是有意压低的次级信息，且被侧栏「属性」与卡片预览共用同一份 `abstract`（nc §2 第 4 行）。要改就是一句话，留在 G3 第 21 条让用户判。
24. **语义胶囊 = 下拉切换（第 15 行，r2）。** 用户要求把第 5 段的语义胶囊改成按钮下拉。做法：触发按钮保持胶囊的样子（同一份类名 `SEMANTIC_PILL` + `pillStyle(semantic.color)`，所以 readOnly 的静态 pill 与它逐像素同形），菜单体**复用**共享的 `SemanticList` —— 它已经带着搜索框、彩色圆点、描述、删除与「Add new type」，是侧栏「属性」里那一份的同源实现，第二份列表必然漂移（§M2.2-3 图标表与 §M3.2-22 类型名表的先例）。选一条走 `patchNode({ semanticId })`，因此**仍然只有宿主的 drain 写节点**；`SemanticList` 自身能打开全局「新建语义」对话框、也能删语义（那是语义目录的写，不是本节点的写，和侧栏点开的是同一个菜单）。**不加箭头**（用户要求）：胶囊本身就是可点提示。
25. **`DropdownMenuContent` 的默认宽度会吃掉共享列表（第 15 行的坑）。** 本仓的 `ui/dropdown-menu.tsx:47` 把内容宽度设成 `w-(--radix-dropdown-menu-trigger-width)` —— 语义胶囊只有 ~90–190px，而 `SemanticList` 是 `w-64`（256px），于是列表**溢出内容盒的 `overflow-x-hidden`**：实测菜单盒 128px、行盒 240px，点击落在 Dialog overlay 上（探针 hit test 直接指出 `under=DIV.fixed inset-0 ... bg-black/10`），表现为「菜单能开、点哪都没反应」。`w-auto` / `w-64` 都可能输给那个 CSS 变量（取决于样式表顺序），所以用 **`min-w-64`**：`min-width` 与 `width` 是不同属性，不受顺序影响（实测菜单 256px、行落在盒内）。
26. **探针的 stub store 必须可订阅、fixture 必须进 store（r1/r2 期间的两次误判）。** ① 原先的 stub `useStore` 只做一次 `selector(state)`，于是「写进 store」不会重渲染 —— 探针把一次**成功**的写入报成「什么都没发生」；改成 `useSyncExternalStore` + 写入后通知（与真实 Zustand 一致）。② `NodeService.upsert` 只更新**已存在**的行，只放在 React state 里的节点写了也白写 ⇒ 探针把节点先 `upsertNode` 进 store，再由宿主从 store 读回（和真实宿主同形）。这两条不是被测代码的问题，但**会让判据说谎**，所以记在这里。
